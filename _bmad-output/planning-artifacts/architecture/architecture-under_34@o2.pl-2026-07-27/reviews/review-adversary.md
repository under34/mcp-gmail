# Adversarial review — Architecture Spine

Reviewed artifact: `ARCHITECTURE-SPINE.md` (draft, 2026-07-27).

The spine has a sound high-level boundary, but its invariants do not yet make independently implemented lower-level components composable. The examples below are deliberately paired: each side can plausibly satisfy every current AD, while their combination produces an incorrect, unsafe, or untestable system.

## Findings

- **The `ThreadSummary` contract is not a contract yet.** AD-6 names fields but not their types, nullability, cardinality, language, action shape, provider identifier, schema version, or validation/error representation. An OpenAI adapter can return `priority: "high"` and `actions: ["Reply"]`; a Claude adapter can return `priority: "wysoki"` and `actions: null`. Both expose the named fields and pass local "validation", yet `compare_summaries` cannot honestly claim one shared schema. This already conflicts with FR-4's Polish priority values. Add a versioned canonical schema, exact enums and JSON types, `actions` empty-list rule, field length limits, provider/model identifiers, and a single domain validator used by both adapters.

- **Status is ambiguously split between a summary and an operation.** AD-6 puts `result status` on every `ThreadSummary`, while AD-7 puts `complete`/`partial`/`failed` on runs and tool responses; neither defines allowed combinations. One provider adapter may emit a useful summary as `partial`, while the write service treats any partial item as a failed run; another may save it and label the run `complete` because all calls returned HTTP 200. Both obey the text, but `get_daily_digest` gives incompatible truth claims. Specify separate, typed `SummaryStatus` and `OperationStatus`, a deterministic aggregation table, mandatory per-item failure reasons, and what is persisted/returned for every combination.

- **The confirmation requirement has no binding protocol.** A FastMCP adapter can preview a normalized filter and accept a later `confirmed=true`; the use case can correctly re-resolve the current filter just before fetch. In the gap, a user or another local client changes the Active Gmail Filter, so confirmation for preview A authorizes fetch B. Both components satisfy AD-5's wording. Define a one-time, expiry-bound confirmation token containing account ID, canonical filter, selected thread IDs or range, provider set, content-transfer purpose, and filter revision; reject mismatches and consume it atomically.

- **There is no immutable filter snapshot or filter revision.** The scheduler can save a run with the query text currently called Active Filter; `compare_summaries` can correctly check the *current* Active Filter. After a filter change, a previously included thread becomes ineligible even though it belongs to the displayed digest, or a thread can become eligible for comparison without fresh user review. Require canonical filter representation, revision/hash, and the exact snapshot on runs, summaries, confirmations, and eligibility decisions; state explicitly whether comparison uses the active snapshot at confirmation time or a digest's snapshot.

- **“New or changed” lacks a shared identity and watermark algorithm.** A Gmail adapter can report a thread as changed from Gmail's `historyId`; a repository can deduplicate using a hash of the visible plain-text body. A label-only update advances `historyId` but not the hash, whereas a new message with identical normalized body changes neither hash nor candidate identity as implemented. Each follows AD-5/AD-7 in isolation, but cost control and inclusion reasons diverge. Define the canonical thread version (for example, Gmail thread ID plus latest message ID/internal date/history ID), the successful-run watermark, filter-entry detection, ordering/pagination snapshot, and handling for deleted/inaccessible threads.

- **The lock rule does not establish a transaction or an idempotency boundary.** A CLI implementation can take and release a per-account file lock around Gmail fetch, then call the write service; an MCP implementation can take the same lock only inside the write service. Two runs can fetch and bill the provider concurrently, then serialize SQLite writes. They technically use the same service and a per-account lock, yet violate AD-3's stated prevention of duplicate costs. Define the lock owner, acquisition point before candidate discovery, lease/stale-lock recovery, lock key, run/idempotency key, and a database transaction that atomically records the run, per-thread versions, summaries, and watermark.

- **Provider comparison does not guarantee comparable inputs.** An OpenAI adapter may summarize a cached, cleaned thread body from the digest; a Claude adapter may fetch the latest thread and apply a different HTML/quote/signature cleaner. They both return valid `ThreadSummary` objects and Claude is only called after explicit confirmation, but the two results are not a model comparison. Define a single application-owned `AnalysisInput` snapshot (thread version, deterministic message order, canonical extraction/redaction/normalization, prompt/schema version) and require both provider calls in `compare_summaries` to consume its exact hash.

- **The sensitive-content boundary is incomplete for transient processing.** AD-4/AD-8 forbid persistence and logs, but do not say where message bodies may be materialized, how long they live, or who cleans them. A Gmail adapter can return raw MIME/HTML with quoted history; a provider adapter can trim at a different point and include email addresses, signatures, or prompt-injection instructions in its request. Neither persists or logs a body, so both meet the ADs, yet privacy, cost, and comparison semantics differ. Make a single application-owned, in-memory content-preparation port/rule mandatory: message selection, HTML-to-text policy, attachment exclusion, quote/signature stripping, size/token cap, redaction policy, and no-content-on-error guarantees.

- **The declared `ThreadSummary` fields cannot support the required digest item.** AD-6 limits the persisted summary contract to summary, priority, actions, provider, and status. FR-3 separately requires an original-thread link/ID and inclusion reason. One repository can keep those as unstructured metadata while the MCP adapter derives its own Gmail link; another can store a different link format or omit the inclusion reason from response. Both comply with AD-6 literally but cannot deliver a stable digest item. Define distinct versioned `ThreadSummary`, `DigestItem`, `Digest`, and `Run` records, with required thread ID, safe source-link construction, inclusion reason enum, filter revision, source version, generation time, and provider/model provenance.

- **Result envelopes have no machine-readable failure contract.** The convention only says `status`, `data`, `reason`. A Gmail adapter can map expired OAuth to a free-text reason with no `data`; the provider adapter can return an empty `data` list and a free-text timeout; the tool adapter can wrap both in `partial`. All meet the convention but clients cannot determine a safe next action and test suites cannot assert interoperability. Specify a versioned tool-response schema, `reason.code`, safe user message, remediation/action enum, correlation/run ID, and precise presence rules for `data` under complete/partial/failed.

- **Retention can permanently poison deduplication and may retain data indefinitely.** AD-8 deletes digests and summaries after 30 days but allows Gmail IDs, content hashes, and metadata to remain without a retention period. One cleanup unit deletes only result rows; the dedup unit still sees an old hash and skips a reappearing or newly changed thread. Another deletes the hash with the summary and silently resummarizes. Both honor the stated cleanup rule, but behavior and privacy differ. Define retention and deletion cascades for every table, the maximum lifetime of hashes/IDs/metadata, and the post-purge deduplication rule; make manual deletion and disconnect atomic over tokens, runs, summaries, hashes, and locks.

- **Time semantics are underspecified at the one point the product schedules work.** The cron adapter can interpret “08:00 local” with its host timezone and advance a wall-clock daily marker; the application can store UTC ranges and calculate “previous successful digest” as 24 hours. On a DST transition or missed cron invocation, the two valid interpretations create gaps or duplicate candidates. Define an IANA timezone setting, scheduled instant calculation, DST gap/fold behavior, successful-watermark semantics instead of a rolling 24-hour period, and the exact covered range convention (inclusive/exclusive).

- **There is no configuration consistency invariant.** Settings are loaded once in `bootstrap/`, but the active filter and provider keys/configuration are mutable local state. A CLI process can load OpenAI model `A` and filter revision `1`; a concurrently started MCP process can save filter revision `2` and model `B`. Each bootstrap complies, yet a persisted run can claim the new active filter while using the old runtime configuration. Require an immutable `RunConfiguration` snapshot captured before lock-protected discovery, including account identity, filter revision, provider/model, prompt/schema versions and timezone, and persist it with the run.

- **“User-only application-data directory” is an aspiration, not an enforceable boundary.** One bootstrap can create the directory under permissive inherited umask and save `token.json`; another can put `.env` in the repository because AD-4 permits local `.env`. Neither leaks to Git and both use the named directory for their chosen data, yet local secrets become readable by other users or placed outside the deletion/retention lifecycle. Define exact application-data and configuration paths, supported OS permission checks/modes, refusal or warning behavior for unsafe permissions, and prohibit secret fallback paths.

- **Schema evolution and recovery are absent despite persistent state.** SQLite adapters can independently introduce tables/columns for summaries and run state, use `CREATE TABLE IF NOT EXISTS`, and each pass fresh-database tests. An upgraded install then has old rows without provider/model/filter revision, and one adapter interprets missing status as `complete` while another rejects it. Specify a migration mechanism, schema/data versioning, forward/backward compatibility policy, startup validation, backup/recovery behavior, and an explicit rule that unknown legacy state is not presented as complete.

- **The non-mutation guarantee does not constrain side effects at the Gmail boundary enough to test it.** A Gmail adapter can use `gmail.readonly` but still call endpoints that alter local OAuth state or use a cached client whose broader existing token is silently reused; a tool handler can truthfully declare no Gmail mutation capability. The ADs do not require runtime scope inspection, allowed Gmail endpoint list, or a contract test preventing modification endpoints. Add an allowlist of read-only Gmail operations, token-scope verification at connection and before use, and adapter contract tests that fail on any Gmail write/modify call.

## Required invariant additions before implementation

1. Versioned domain schemas for summaries, digest/run records, tool envelopes and typed errors/status aggregation.
2. An atomic analysis-run protocol: configuration/filter snapshot, confirmation token where required, lock-before-discovery, idempotency key, transactional commit, and watermark advancement only on the defined successful outcome.
3. One deterministic `AnalysisInput` preparation pipeline and snapshot hash shared by OpenAI and Claude calls.
4. Explicit lifecycle rules for filter revisions, account identity, retention/deletion, schema migrations and schedule time.
5. Enforceable local-security and Gmail-read-only adapter contracts, not only architectural intent.
